## 2. Mathematical, Precision & Algorithmic Audit Foundations

### 2.1 Floating-Point Precision Handling: Single vs. Double Precision (`float32` vs. `float64`)
The C# HiStrA architecture combines single precision (32-bit `float` / `Single`) and double precision (64-bit `double` / `Double`) across distinct architectural tiers:

1. **Geometric Layer & Vector Transformations (`float32`)**:
   - In C#, Microsoft XNA `Microsoft.Xna.Framework.Vector3` is backed by IEEE-754 32-bit single-precision floating-point numbers.
   - In `Quad.GetDisplacementFromShearDOF` (`Objects/Quad.cs:4017–4065`) and `InterfaceOperations.PrepareBuildInterface` (`InterfaceOperations.cs:1074–1100`), intermediate corner warping vectors $\mathbf{\psi}_k$, local triad frame unit vectors $(\mathbf{e}_1, \mathbf{e}_2, \mathbf{e}_3)$, and cross products are evaluated in single precision.
   - In Python, `histra/preprocessing/afference.py` and `histra/preprocessing/contact_geometry.py` explicitly emulate this behavior using `_f32`, `_dot3_f32`, `_cross3_f32`, and `_unit_f32` primitives. This prevents 64-bit coordinate drift and ensures that Python produces identical triad orientations and local coordinates to C#.
   - **Threshold Cutoff Invariant**: In C# `AfferenceMatrix.SetFromCoefficients`, kinematic transformation coefficients satisfying $|T_i| \le 1.0 \times 10^{-4}$ are explicitly truncated to zero to preserve sparsity. Python strictly enforces this identical $1.0 \times 10^{-4}$ cutoff.
2. **Constitutive Modeling & Nonlinear Solver (`float64`)**:
   - Element strain increments, stresses, internal resisting force vectors $\boldsymbol{F}_{\text{int}}$, tangent stiffness matrices $\boldsymbol{K}_T$, and linear solver solutions are strictly 64-bit `double` in C#.
   - In Python, all compiled Numba kernels in `histra/solver/hysteretic_kernels` operate on `np.float64` contiguous arrays, ensuring exact double-precision arithmetic throughout equilibrium solving.
3. **Explicit Single-Precision Casting Quirks in C#**:
   - In `Quad.SetNonLinearProperties` (`Objects/Quad.cs:4403, 4445`):
     ```csharp
     while ((double)num7 < Math.Pow((double)Convert.ToSingle(num3), 2.0))
     ```
     C# explicitly casts the integer grid boundary `num3 = 100` to `Single` before converting back to `Double`. Python's `quad_yield_search` accurately accounts for this boundary specification.
   - In `Quad.ComputeStaticLoadInternal` (`Objects/Quad.cs:3170`), surface load numerical integration uses a 32-bit floating-point accumulator, which Python reproduces in `histra/elements/quad_static_load.py` (`_sum4_f32`).

### 2.2 Transcendental Function Behavior: `Math.Pow`, `Math.Atan`, `Math.Sqrt`, and CRT ULP Nuances
1. **`Math.Pow` and CRT Runtime Discrepancies**:
   - In Windows .NET Framework 4.8, `Math.Pow(x, y)` delegates to the Microsoft Visual C Runtime library (`ucrtbase_clr0400.dll` or `msvcr120_clr0400.dll`).
   - In Linux POSIX `libm` and LLVM/Numba, `pow(x, 0.5)` or general power functions may evaluate via glibc polynomial approximations or LLVM vector intrinsics. This introduces 1-to-2 ULP (Units in the Last Place) differences in the least significant bits.
   - In `Quad.SetNonLinearProperties`:
     ```csharp
     radius = Math.Pow(Math.Pow((num39 - num40) / 2.0, 2.0) + Math.Pow(num41, 2.0), 0.5);
     ```
     C# intentionally nests `Math.Pow(..., 0.5)` rather than invoking `Math.Sqrt`. Python isolates these differences in `histra/_framework_math.py` via `csharp_pow`, binding to the Windows CRT when available while providing standard IEEE-754 approximations on Linux.
2. **`Math.Atan` Friction Angle Softening**:
   - In `SpringCoulomb03`, friction angle $\phi$ degrades as a function of cumulative plastic shear work using `Math.Atan`:
     $$\phi = \phi_0 - (\phi_0 - \phi_{\text{res}}) \cdot \frac{2}{\pi} \arctan(\beta \cdot W_p)$$
     Python mirrors this formulation identically via `math.atan` and `csharp_atan`.
3. **`Math.Sqrt` Reciprocal Normalization**:
   - In C#, `Vector3.Normalize` computes reciprocal square roots in single precision: `1.0f / (float)Math.Sqrt(len_sq)`. Python's `_unit_f32` in `contact_geometry.py` replicates this normalization sequence.

### 2.3 Branch Decision Logic Quirks
1. **Tangent Matrix Refresh Schedule (`_is_standard_method`)**:
   - In `SolverRuntime/NumericalProcedure/NewtonRaphson.cs:26–28`:
     ```csharp
     if ((an.Method == AnalysisMethodEnum.StandardNewtonRaphson ||
          an.Method == AnalysisMethodEnum.StandardBisectionLineSearch ||
          an.Method == AnalysisMethodEnum.StandardRegulaFalsiLineSearch ||
          an.Method == AnalysisMethodEnum.StandardSecantLineSearch) && alfa != 0.0)
     {
         base.theIntegrator.UpdateK(p, Collections, ref alfa, false);
     }
     ```
   - Tangent stiffness $\boldsymbol{K}_T$ is refreshed during iteration $k \ge 1$ *only* for Standard methods and *only* when $\alpha \neq 0.0$. If $\alpha == 0.0$, tangent reformation is skipped.
   - In Modified Newton-Raphson, $\boldsymbol{K}_T$ is formed once at iteration 0 and held constant throughout all subsequent equilibrium corrections.
2. **Line Search Step-Length Clamping in Regula-Falsi**:
   - In `SolverRuntime/LineSearch/RegulaFalsiLineSearch.cs:65–77`:
     ```csharp
     num2 = num3 - num5 * (num4 - num3) / (num6 - num5);
     if (num2 > this.maxEta) num2 = this.maxEta;
     if (num7 > num) num2 = 1.0;
     if (num2 < this.minEta) num2 = this.minEta;
     ```
   - If the residual energy ratio `num7` increases above initial ratio `num`, C# forces the step multiplier `num2 = 1.0` *before* applying the lower bound `minEta`. Python's `RegulaFalsiLineSearch` reproduces this exact clamping order.
3. **Quad Yield Search Cumulative Extrema**:
   - In `Objects/Quad.cs:SetNonLinearProperties`:
     Variables `num4` (maximum principal stress) and `num5` (minimum principal stress) are declared outside the deformation sign loop (`for (int i = 0; i < 2; i++)`). They accumulate extrema across both passes rather than resetting between positive and negative distortional deformations. Python strictly preserves this cumulative extrema behavior.

### 2.4 Convergence Criteria & The Work Increment Trap
1. **Unbalanced Force Norm (`CTestNormUnbalance`)**:
   - Evaluates residual norm: $\|\boldsymbol{R}\|_2 / \|\boldsymbol{R}_0\|_2 \le \text{tol}$ or $\|\boldsymbol{R}\|_2 \le \text{tol}$.
2. **Displacement Increment Norm (`CTestNormDispIncr`)**:
   - Evaluates incremental displacement norm: $\|\delta\boldsymbol{u}\|_2 / \|\boldsymbol{u}\|_2 \le \text{tol}$.
3. **Incremental Work (`CTestEnergyIncr`) — The False Convergence Trap**:
   - Evaluates work increment: $\frac{1}{2} |\delta\boldsymbol{u} \cdot \boldsymbol{R}| \le \text{tol}$.
   - **Critical Gotcha**: If displacement increment $\delta\boldsymbol{u}$ is tiny or nearly orthogonal to unbalance vector $\boldsymbol{R}$, the dot product $\delta\boldsymbol{u} \cdot \boldsymbol{R}$ approaches zero, falsely signaling convergence while the active force residual $\|\boldsymbol{R}\|_2$ remains huge.
   - **Safety Architecture**: Python implements `CTestEnergyIncr` for exact C# step-matching, but complements it with an independent dual-mode `EquilibriumAudit` (`histra/solver/equilibrium.py`) to verify true physical force and reaction balance.

### 2.5 Algebraic Order of Operations & Linear System Invariants
1. **Quad Diagonal Yield Force Association**:
   - In `Quad.cs:4470–4472`:
     ```csharp
     array7[i] = num6 * Math.Min(Math.Abs(Fyt / num4), Math.Abs(Fyc / num5));
     array8[i] = this.DAlfa2DDiag() * array7[i];
     array[i] = k * array8[i];
     ```
   - Because floating-point multiplication is non-associative, `k * (dalfa * scale)` yields a slightly different bit representation than `(k * dalfa) * scale`. Python's `quad_yield_search` strictly follows `k * (dalfa * scale)`.
2. **Linear System Reset Invariant**:
   - In `MatrixManager/LinearSystem.cs`:
     - `ResetStiffnessMatrix()` clears matrix $\boldsymbol{K}$ only.
     - `ResetLoadVector()` clears vector $\boldsymbol{b}$ only.
   - In C#, `NewtonRaphson.cs` forms the residual vector into $\boldsymbol{b}$ *before* updating $\boldsymbol{K}$. If rebuilding $\boldsymbol{K}$ inadvertently cleared $\boldsymbol{b}$, the assembled unbalance vector would be lost, causing catastrophic solver divergence. Python's `LinearSystem` enforces this strict isolation.
